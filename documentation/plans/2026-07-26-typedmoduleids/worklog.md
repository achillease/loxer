| 2026-07-31 19:28 | [Implementation] `Loxer.init({ modules })` checked against the registry | Follow-up asked for by the user: the registry typed every *consumer* of a module id but not the *declaration*, so an augmented project could still define a module it never registered and omit one it did. Added `RegisteredModules<M = unknown>` (`src/types.ts`): `LoxerModules` while the registry is empty, otherwise `Record<registered, Module> & Partial<Record<DefaultModuleId, Module>> & { [K in keyof M]: K extends ModuleId ? Module : never }`. `LoxerOptions` gained `<M extends LoxerModules = RegisteredModules>` with `modules?: M`, and `init<M extends RegisteredModules<M>>` / `initLoxer<M extends RegisteredModules<M>>` infer it. The `M` parameter is what catches an unregistered id in an object declared *elsewhere*, where no excess property check applies — its key resolves to `never`; the missing-id half comes from the plain `Record`. `LoxerModules` deliberately stays a loose index signature: it is the `satisfies` target the registry is derived from, so making *it* strict would make `typeof modules` circular ("referenced directly or indirectly in its own initializer"). Verified the mechanics in a scratch program first, for both an augmented and an empty registry, including that a non-generic `init(props?: LoxerOptions)` on `LoxerInstance` still satisfies the generic interface member (parameter bivariance again — `src/Loxer.ts` needed zero edits). Gate: 9 new cases in `test/types/registry.test-d.ts` (inline/variable/spread extras, missing id, `: LoxerModules` annotation, `satisfies LoxerOptions`, both `Loxer.init` and `@initLoxer`); the pre-existing "levels are names, never numbers" case had to move onto a registered id, because an unregistered `X` would now error for the wrong reason. `pnpm build`/`lint`/`test` (18 files, 245 tests)/`typecheck:test`/`typecheck:types` 0, demo `tsc --noEmit` 0, `pnpm docs` 0 errors. Left as-is: `modules` stays optional, so a bare `Loxer.init()` under an augmented registry is still accepted — several packages may share one registry, and conditioning the property's optionality on the registry would make `Loxer.init({ dev: true })` an error while `Loxer.init()` compiles. |
