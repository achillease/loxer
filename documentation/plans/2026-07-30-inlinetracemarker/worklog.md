| 2026-07-30 01:50 | [Implementation] Decision: arrows read their own parameters | An arrow has no `arguments`, and wrapping it in a rest-parameter wrapper — the statement form's answer — would move the options expression out of the scope it was written in, where it can read the arrow's parameters. So an arrow's recorded arguments are built from its parameter list instead. A destructuring parameter cannot be read as a whole, so it is exchanged for a generated name and re-declared as `let <pattern> = _traceArg;` above the traced body: `Function.length` does not move (a name and a pattern each occupy one parameter), `let` keeps a reassignable parameter reassignable, any type annotation moves onto the generated parameter, and the bindings stay in the scope the options and the body both read them from. The accepted consequence is that a defaulted parameter records its effective value where `arguments` would have recorded nothing. |
| 2026-07-30 01:50 | [Implementation] Decision: options may not read the body | The transform moves the marked body into a nested `_invokeTrace` arrow, so an options expression referencing something the body declares — `trace({ moduleId: MOD })` above a `const MOD` — would compile to a `ReferenceError` instead of the TDZ error it is today. `assertOptionsPrecedeBody` rejects it by name; parameters (`binding.kind === 'param'`) stay readable, which is the case that actually matters. Only an object literal reaches this form, so a bare `trace(OPTS)` or `trace(makeOptions())` is still read as the statement form and keeps its own diagnostic. |
